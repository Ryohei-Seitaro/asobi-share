# CEOゴール：遊び・旅行シェアアプリ（仮）の事業構想検証とMVP設計

CEOとして新しく創りたいアプリの構想が出てきた。構想段階のため、事業性の検証・North Star策定・MVPスコープ確定・技術/法務要件定義までを一気通貫で依頼したい。

## 1. コンセプト（CEOの言葉のまま）

**「note に Instagram の要素を組み込んだ、遊び・旅行のシェアアプリ」**

- 遊びや旅行の内容を、**写真＋旅程（時間軸つき）**で投稿してシェアする
- 「今週の土日何しようかなー」と考えている 18〜20代がメインターゲット
- その層は友達と会うと「先週何してたん？」「おすすめの旅程は？」という会話をしている。そこがそのままコンテンツになる

### 投稿されるコンテンツの想定
- デート（こんなデートした）
- 海外旅行（こんな海外旅行した／この時間にこれをした）
- 国内旅行
- 合宿（こんなスケジュールでやった）
- サークル遊び
- 家族旅行

上記はそのままタグ／カテゴリ分類の候補。

### 差別化の核：「計画と実際」
旅行は考えるときに結構苦労するし、行ったら計画と異なることも起きる。
- 投稿を**「計画」と「実際」**の2層構造で持たせたい
- 行った**後からコメントを追記**できるようにする
- 「行ったときに気をつけた方がいいこと」を載せられるようにする

## 2. ユーザーインセンティブ設計（CEOの仮説）

3つの欲求を同時に満たす設計にしたい：
1. **自慢したい欲求**を満たす（SNS的承認）
2. **自分の旅行を売れる**（旅程がコンテンツとして換金される）
3. **思い出として残す**インセンティブが生じる（アーカイブ価値）

具体的な仕組みの案：
- **シェア数が一定数に到達すると報酬がもらえる**
- **投稿者自身が値付けして販売できる**（有料旅程）
- 作った投稿は**外部SNSにシェアできる**

そして読み手側は「明日なにしようかなー」というときにこのSNSを見に来る。

## 3. マネタイズ（CEOの仮説）
- 旅行系の広告収益
- ユーザーがマネタイズした売上の一部をレベニューシェアで取る

## 4. 決済
- **Stripe でいけるか**を確認したい（CEOの疑問。技術基盤室＋コーポレートで検証すること）

## 5. ビジョン
**「個人のエンタメ力をエンパワーメントする会社」**

# 依頼内容

## A. 経営企画室（researcher / bizdev）

### A-1. 市場・競合分析
18〜20代の「週末・旅行の予定を決める」行動の実態と、既存の代替手段を洗い出すこと。少なくとも以下との差分を明確にすること：
- Instagram / TikTok（旅行リール・スポット検索としての実態）
- note / Brain 等の有料コンテンツ販売プラットフォーム
- 旅行系メディア（RETRIP・ことりっぷ 等）
- 旅のしおり／旅程共有系アプリ（過去に多数が失敗している領域。**なぜ失敗したのかを必ず調べること**）
- Google Maps の保存リスト、TimeTree 等

### A-2. コンセプト検証（最重要・辛口で）
CEO仮説の弱点を潰すこと。特に以下は正面から検証すること：
1. **「旅程は本当に金を払って買われるのか」** — 18〜20代は可処分所得が低い。有料販売のGMVは立つのか
2. **コールドスタート問題** — 見に来る人がいないとシェア報酬も販売も成立しない。鶏卵をどう割るか
3. **「シェア数で報酬」の原資はどこから来るのか** — 広告収益が立つ前の初期はキャッシュアウトのみ。持続可能か
4. **投稿コストの高さ** — 写真＋旅程＋計画/実際の追記は投稿負荷が高い。Instagramの手軽さに勝てるか
5. 上記を踏まえ、**このまま進めるべきか／ピボットすべきか／やめるべきか**を明確に判定すること

### A-3. 既存事業との関係整理（CEO判断済み・前提として扱うこと）

**CEO決定：memori との統合はしない。本件は独立した新規事業として立てる。**
ただし memori（3D Memory：場所×時間×仲間／絵日記・マップ・タイムライン・写真アップロード実装済み・VPS稼働中）は、
**一部機能を流用する可能性がある**。

したがって依頼は「統合すべきか」ではなく、以下に限定する：
- memori の実装資産のうち、**どのコンポーネントが本アプリに転用可能か**を具体的に列挙すること
  （例：写真アップロード・圧縮処理、マップ表示、タイムラインUI、場所×時間のデータモデル）
- 転用する場合の**コピーして分岐させる／共通ライブラリ化する**のどちらが妥当か、技術基盤室と合わせて判断すること
- 転用によって削減できる工数を見積りに反映すること
- **両プロダクトのターゲットとNorth Starが混ざらないよう、境界線を明確に定義すること**

### A-4. North Star策定
ビジョン「個人のエンタメ力をエンパワーメントする会社」を、プロダクトのNorth Star（1文）とNorth Star Metricに落とすこと。

## B. 事業開発室（プロダクト設計）

### B-1. コアループ確定
投稿者側／閲覧者側それぞれのループを定義し、両者が噛み合うループ図を示すこと。

### B-2. MVPスコープ確定
「計画と実際」「有料旅程」「シェア報酬」「タグ分類」「外部SNSシェア」のうち、**MVPに入れるものと後回しにするものを判断し、理由を付けること**。CEOは全部やりたいが、最小で検証できる構成を提示してほしい。

### B-3. 投稿UXの設計
投稿負荷が最大のリスク。旅程入力をどこまで簡略化できるか（写真のEXIF位置情報・時刻からの自動旅程生成など）を含めて設計すること。

## C. 技術基盤室（engineer）

### C-1. 技術要件定義
- システム構成図（投稿・写真ストレージ・旅程データモデル・タイムライン配信・決済）
- 技術スタック（既存資産の流用前提で。lifeos / signal-media の Clerk + Neon 構成、memori の写真・マップ・タイムライン実装が流用候補）
- 「計画」と「実際」を持つ旅程のデータモデル設計
- 実装難度と工数見積り（週単位）

### C-2. Stripe実現性検証（CEOの明示的な疑問）
- ユーザー間のコンテンツ販売（C2C）を **Stripe Connect** で実装できるか。可否と推奨構成（Express/Standard、charge type）を明示すること
- 「シェア数に応じた報酬支払い」をStripeでどう実装するか（Payouts / Transfers）
- 手数料構造を踏まえ、少額決済（数百円の旅程販売）で経済が成立するか試算すること

## D. コーポレート（legal / backoffice）

### D-1. 法務論点の洗い出し
最低限、以下は判定すること：
- 個人間のコンテンツ売買を仲介することの **資金決済法**（収納代行／資金移動業）該当性
- **特定商取引法**の表示義務（プラットフォーム／出品者どちらが負うか）
- 投稿写真の**著作権・肖像権**（同行者が写り込む前提のアプリであるため必須）
- 「シェア数で報酬」の**景品表示法**該当性
- 旅行の旅程を販売することが**旅行業法**に抵触しないか（重要：旅程の"手配"に踏み込むとリスク）
- 未成年ユーザー（18歳前後）が収益を得ることの取扱い

## E. 最終アウトプット

以下を1本のレポートにまとめ、CEOが「やる／やらない／どう変えるか」を即断できる形にすること：
1. 事業性判定（GO / 条件付きGO / PIVOT / NO GO）と根拠
2. North Star と North Star Metric
3. memori との関係の結論
4. MVP機能一覧（入れる／後回しの線引き付き）
5. 技術構成と工数見積り
6. Stripe実現性の結論
7. 法務リスク一覧と対応方針
8. 次の30日でやるべきことTop3

**忖度不要。CEOの仮説が弱いところは弱いと書くこと。**
